1. 设计总览

本方案在不改动服务端的前提下，于 Android 端新增一条与相册同步并行的手动备份链路。核心思路：复用现有上传/校验/前台服务的骨架，新建面向文件系统的浏览、选择、编排三模块。

三条核心设计决策：
  1. 服务端零改动——verify-sync 请求只带 fileHash（不带 relativePath），绕过服务端路径守卫（FileService.java#L668-L672），使同一内容无论在相册还是 phoneBackup 目录都能命中；命中后按返回的 remotePath 前缀区分来源。上传时 relativePath=phoneBackup/<设备名>/... 走既有落盘逻辑。
  2. ChunkUploader 零改造复用——文件系统路径通过 Uri.fromFile(file) 转为 file:// URI 传入 uploadMedia()，分片/断点续传/秒传全链路不变。
  3. SyncRecord 表零扩展复用——手机备份记录以 localUri = 文件绝对路径、mediaType = null、mediaId = null 写入，与相册同步记录共存于同一张表。

2.2 新建模块说明

① LocalFileBrowser —— 文件系统浏览

  • 职责：以 java.io.File 遍历主存储根目录（Environment.getExternalStorageDirectory()）的目录树，返回排序后的文件夹/文件列表。
  • 根路径：/sdcard/（即 Environment.getExternalStorageDirectory()），用户进入后可逐级下钻。
  • 排序规则：文件夹在前、文件在后，各自按名称升序；默认过滤 "." 开头隐藏项。
  • 文件夹统计：递归计算子文件数（用于显示"共 x 项"），统计在后台线程执行不阻塞 UI。
  • 不可读目录：File.canRead() == false 的条目标记置灰。
  • 与 MediaScanner 的区别：MediaScanner 走 MediaStore 只能取照片/视频/音频；LocalFileBrowser 走 File API 可取任意类型文件。

② BackupStatusResolver —— 两级去重判定

  • 职责：对浏览到的每个文件判定备份状态，按 PRD FR-04 的命中顺序：
    1. 第一级（本机记录）：查 SyncRecordDao.findByUriAndHash(absPath, hash)，若存在有效 remoteFileId → 已备份·来源按 remotePath 前缀判定。
    2. 第二级（云端指纹批量校验）：未命中本机记录的文件，计算 SHA-256 后交给 FileHashVerifyScheduler 分批发往 verify-sync。
  • 关键差异：非媒体文件没有 capturedAt（拍摄时间），只走指纹通道，不能走 rebuildByPathSizeCapturedAt 备用通道。
  • 状态回填：先展示"校验中…"，异步回填，不阻塞浏览。

③ FileHashVerifyScheduler —— 指纹批量校验调度

  • 职责：对齐现有 SyncVerifyScheduler 的窗口节流 + 分页模式，但 Target 面向文件系统项而非 MediaStore 项。
  • 分页：每批 50 条（PAGE_SIZE = 50），单线程 Executor，DEBOUNCE_MS=300，WINDOW_INTERVAL_MS=10min。
  • Target 主键：stableKey = 文件绝对路径（而非 MediaStore content URI）。
  • 请求构造（关键）：VerifySyncItem 只填 fileHash + fileSize + fileName，不填 relativePath、不填 capturedAt、不填 mediaId——使服务端 rebuildByFileHash 的路径守卫（L668-672）不触发，任何位置的相同内容都能命中。
  • 响应处理：命中后按返回 remotePath 前缀区分：phoneBackup/ 开头 → 已备份·手机备份；photos/|videos/|audio/ 开头 → 已备份·相册；其他 → 已备份·其他。未命中 → 未备份。
  • 本机记录写入：校验命中后，将 remoteFileId + remotePath + fileHash 写入 SyncRecord，下次直接命中第一级。

④ BackupEngine —— 同步编排

  • 职责：接受显式的 List<BackupItem>（文件绝对路径 + 目标 relativePath），循环调用 ChunkUploader.uploadMedia()，统计成功/跳过/失败。
  • 与 SyncEngine 的区别：SyncEngine 从 MediaScanner 扫全量媒体；BackupEngine 接受用户显式选择的文件列表，不做扫描。
  • 取消机制：对齐 SyncEngine 的 AtomicBoolean cancelRequested，每轮循环检查。
  • 单文件失败不中断：try-catch 包裹单个文件上传，失败计入 failed 列表，继续下一个。
  • 秒传处理：ChunkUploader 上传时已携带 hash，服务端确认内容存在抛 DuplicateSkipException → 计入 skipped。
  • 进度回调：通过 ChunkUploader.ProgressListener 上报单文件百分比，汇总后经 BackupProgressBus 推送到 UI。

⑤ BackupForegroundService —— 前台服务

  • 职责：对齐 SyncForegroundService 的通知栏 + 前台保活模式，但驱动 BackupEngine 而非 SyncEngine。
  • Intent：ACTION_BACKUP_SYNC（携带选中的文件列表序列化）+ ACTION_BACKUP_CANCEL。
  • 互斥：复用 AtomicBoolean SYNCING 或新建独立 BACKUP_SYNCING，防止与相册同步并发冲突（建议独立，两条链路并行）。
  • 通知渠道：新建 backup_channel，避免与相册同步通知互相覆盖。

⑥ DeviceNameProvider —— 设备名管理

  • 默认值：Build.MODEL（如 Mi14）。
  • 持久化：SharedPreferences key phone_backup_device_name。
  • 非法字符清洗：正则 [/\\:*?"<>|] + 首尾空格/点号 → _，长度截断 32，清洗后为空回退 Android设备。
  • 生效范围：编辑后立即写入 Prefs，仅影响此后新上传文件的 relativePath，不迁移历史目录。

3. 服务端零改动验证

本节逐项证明服务端不需要任何代码变更即可支撑手机备份功能。

3.1 verify-sync 路径守卫规避

FileService.java 的 rebuildByFileHash（L655-L674）有一段路径守卫：

// FileService.java L668-672 String clientPath = PathUtil.normalizeRelative(item.getRelativePath()); if (clientPath != null && !clientPath.isEmpty() && !clientPath.equals(matched.getRelativePath())) { return null; // 路径不一致 → 判失败 }
规避方式：手机备份的 verify-sync 请求不传 relativePath（置 null 或空）。守卫条件 clientPath != null && !clientPath.isEmpty() 不成立，直接跳过，matched 命中后正常返回 toRebuiltSyncRecord——其中 remotePath = matched.getRelativePath()，客户端据此区分来源前缀。

由于手机备份的文件可能是任意路径（Download/发票/a.pdf），与相册同步路径（photos/2024/01/a.jpg）天然不同，若传 relativePath 会 100% 触发守卫失败。因此不传 relativePath 是设计上的必然选择，而非权宜之计。

3.2 upload/init 落盘路径

ApiClient.initUpload 签名（L135-136）：

// ApiClient.java public UploadInitResult initUpload(String fileName, String relativePath, long totalSize, String mimeType, String sha256, Long capturedAt)

手机备份调用时传入 relativePath = "phoneBackup/" + deviceName + "/" + 手机相对路径。服务端 DiskIndexService.java（L190-206）按 userId 解析用户根目录，将 relativePath 作为子路径逐级创建，逻辑与相册同步的 photos/... 完全一致，无需改动。

场景relativePath 传参服务端行为结果
手机备份上传phoneBackup/Mi14/Download/发票/a.pdf逐级创建目录，落盘文件✓ 零改动
手机备份 verify-sync不传（null/空）路径守卫跳过，按 hash 匹配✓ 零改动
秒传命中上传 init 带 hash服务端发现 hash 已存在 → 返回已上传✓ 零改动
覆盖上传（文件已修改）同路径 + 新 hash服务端覆盖旧内容✓ 零改动

3.3 磁盘索引与文件可见性

  • DiskIndexService 扫描用户根目录下所有文件，phoneBackup/ 子目录自动纳入扫描范围，上传完成后即在网盘列表可见。
  • CloudFile 实体（L20-71）已具备 sha256、fileSize、relativePath 字段，是统一事实源，手机备份文件写入后与相册文件行为一致。
  • 手机备份产出的文件不出现在相册/视频/音频分类视图——服务端按 relativePath 前缀过滤，phoneBackup/ 不在媒体分类查询范围内。
结论：服务端 FileService、DiskIndexService、CloudFile、上传控制器均零改动。本次改动全部在 Android 端。

4. 数据模型

4.1 SyncRecord 复用（零扩展）

现有 SyncRecord 表（sync_records）字段完全够用，手机备份记录按以下方式填充：

字段相册同步（现有）手机备份（本次）
localUricontent://media/... URI文件绝对路径（如 /sdcard/Download/发票/a.pdf）
localPath可选辅助字段同 localUri（绝对路径）
mediaIdMediaStore _IDnull（文件系统无媒体 ID）
mediaTypeIMAGE / VIDEO / AUDIOnull（非媒体）或按扩展名推断的泛类型
fileName文件名文件名（一致）
fileSize大小大小（一致）
fileHashSHA-256SHA-256（一致）
modifiedAtMediaStore DATE_MODIFIEDFile.lastModified()
remotePathphotos/... / videos/...phoneBackup/<设备名>/...
remoteFileId云端 files.id云端 files.id（一致）
syncedAt同步时间同步时间（一致）
唯一索引兼容性：SyncRecord 的唯一索引为 (localUri, fileHash)。手机备份的 localUri 是文件绝对路径，与相册同步的 content URI 天然不重叠，不会冲突。同一文件通过相册同步和手机备份分别命中时，两条记录独立存在、各自指向不同的 remotePath，符合 PRD"同一份内容不重复存"的语义（秒传保证物理不重复）。

4.2 UploadTask 复用

UploadTask 表已具备 localUri、relativePath、fileSize、fileHash、mediaType 字段，手机备份上传时直接写入，断点续传的 uploadedChunks 机制不变。

4.3 内存模型（新建，非持久化）

模型字段用途
BackupItem absPath · fileName · fileSize · relativePath(目标) · fileHash(lazy) · status 单个待备份文件项，BackupEngine 的输入单元
BackupSelection Map<absPath, BackupItem> · totalSize · totalFiles · skippedCount 跨目录选择集，支持递归展开文件夹后去重

5. 流程：浏览与状态回填（FR-03 / FR-04）

5.1 进入与授权

用户点击「手机备份」按钮（CloudFragment.btnPhoneBackup） startActivity → PhoneBackupActivity
↓
StoragePermissionHelper.checkManageStorage() Android 11+ 检查 ACTION_MANAGE_APP_ALL_FILES_ACCESS_PERMISSION；10 及以下走 READ_EXTERNAL_STORAGE 运行时授权
↓
未授权？展示授权引导页（FR-02），点击「去授权」跳转系统设置 onResume 自动复检；授权后进入浏览
↓
已授权 → 加载根目录 LocalFileBrowser.listDir(Environment.getExternalStorageDirectory()) 子线程执行；返回 List<FileEntry>（文件夹在前/文件在后，按名排序，过滤隐藏项）
↓
UI 先渲染列表（全部"校验中…"状态），不等待状态判定 浏览不被阻塞；文件夹统计项后台递归计算

5.2 状态回填（两级去重）

BackupStatusResolver.resolveBatch(visibleFiles) 对当前可见的文件项批量判定
↓
第一级：本机 SyncRecord 查询 SyncRecordDao.findByUriAndHash(absPath, hash) 需要先算 hash；对于已有 hash 缓存的文件直接查；本机命中且 remoteFileId 有效 → 已备份·来源按 remotePath 前缀判定
↓ 未命中
第二级：FileHashVerifyScheduler 调度 DEBOUNCE 300ms 去抖 → 收集 50 条/批 → 单线程提交 verify-sync
↓
构造 VerifySyncItem：只填 fileHash + fileSize + fileName 不填 relativePath、不填 capturedAt、不填 mediaId——规避服务端路径守卫
↓
ApiClient.verifySyncItems(batch) → POST /api/files/verify-sync 服务端 rebuildByFileHash 按 userId + sha256 查本人文件
↓
响应处理：命中 → 按 remotePath 前缀标来源（phoneBackup/ → 手机备份；photos|videos|audio/ → 相册）→ 写 SyncRecord 未命中 → 标记未备份
↓
UI 回填：notifyItemChanged 刷新对应行徽标 文件夹汇总"已备份 y / 共 x 项"随子项更新动态变化
节流策略对齐 SyncVerifyScheduler：DEBOUNCE_MS=300（停止滚动 300ms 后触发），WINDOW_INTERVAL_MS=10min（同一窗口 10 分钟内不重复校验），避免频繁网络请求。

6. 流程：选择与同步执行（FR-05 / FR-06）

6.1 选择与发起

用户长按/勾选进入多选模式 BackupSelection.add(item) 选中文件夹 → 递归展开为子文件列表加入选择集；跨目录选择保留
↓
底部操作栏实时计算：totalFiles · totalSize · skippedCount 已备份项计入跳过数；"将上传 n 项 · x.x GB，跳过已备份 m 项"
↓
点击「开始备份」（实际上传项 ≥ 1 时可用） 若存在"校验中"的选中文件，先等待其校验完成
↓
构造 BackupItem 列表：每个文件计算 relativePath = "phoneBackup/" + deviceName + "/" + 手机相对路径 设备名经 DeviceNameProvider 清洗
↓
启动 BackupForegroundService Intent.ACTION_BACKUP_SYNC + 序列化 BackupItem 列表 页面切换到进度态

6.2 同步执行

BackupForegroundService.onStartCommand startForeground + 创建通知 BACKUP_SYNCING.compareAndSet(false, true) 防并发
↓
BackupEngine.sync(items, callback) 新线程 对齐 SyncEngine.syncItems 的线程模型
↓
循环遍历 BackupItem（检查 cancelRequested） 每轮上报 onProgress(current, total, fileName)
↓
ChunkUploader.uploadMedia(Uri.fromFile(file), fileName, null, lastModified, 0, 0, relativePath, listener) file:// URI 传入；mediaType=null, takenAt=0, mediaId=0（非媒体）
↓
ChunkUploader 内部：computeHash → 查本机 SyncRecord → ApiClient.initUpload(hash) → 秒传/分片上传 → 写 SyncRecord 秒传抛 DuplicateSkipException → BackupEngine 计 skipped；正常完成计 success
↓
单文件失败 try-catch：计入 failed 列表，继续下一个 网络/存储异常、源文件不存在等
↓
全部完成 BackupProgressBus.notifyCompleted(success, skipped, failed, lastError) UI 切换到结果页
ChunkUploader 复用关键点：uploadMedia() 内部 getSize(uri) 和 computeHash(uri) 均通过 contentResolver.openFileDescriptor(uri, "r") 读取，对 file:// URI 天然支持，无需改造。

7. 流程：取消与重试（FR-07）

7.1 取消

用户点击「取消同步」 → 发送 ACTION_BACKUP_CANCEL Intent BackupEngine.requestCancel() → cancelRequested.set(true)
↓
当前文件在当前分片传输完成后中止 ChunkUploader 循环检查上传任务取消标记；已上传分片保留在 UploadTask
↓
已完成的文件保留在云端，标记已备份；未开始的不再传输 BackupProgressBus.notifyCancelled(synced, skipped, failed)
↓
结果页显示「已取消」 + 成功/跳过/失败分项 已取消的文件下次进入仍为未备份，可重新发起

7.2 重试失败项

结果页点击「重试失败项」（failed.size > 0 时可用） 仅对 failed 列表中的 BackupItem 重新构造一轮同步
↓
重新启动 BackupForegroundService，传入失败项子集 规则不变：秒传/断点续传/单文件失败不中断
↓
完成后合并到原结果或展示新一轮结果 对齐 PRD FR-07「重试仅对失败项重新执行一轮」

7.3 应用被杀/重启

  • 前台服务通知随进程结束而消失；未完成文件状态仍为未备份。
  • 已完成文件因有 SyncRecord 本机记录，重新进入目录时第一级直接命中已备份。
  • 断点续传：UploadTask 表保留了已上传分片，重试时 ChunkUploader 从 init 恢复 uploadedChunks 继续上传。

8. 复用边界矩阵

10. 风险与对策

风险影响对策
file:// URI 在部分定制 ROM 上 openFileDescriptor 失败 上传/指纹计算异常 fallback 用 FileInputStream 直接读取（HashUtils/FileSizeProvider 加 File 重载）
递归选择超大文件夹（如 WeiXin 208 项）导致选择集膨胀 内存占用、UI 卡顿 BackupSelection 用 Map 懒展开；底部统计异步计算；超大批量分批上传时进度通知节流
SHA-256 计算大文件耗时（如 1GB 压缩包） 状态回填慢、浏览体验差 指纹计算在后台单线程；大文件优先显示"校验中…"；同步发起时若仍在计算，上传时 ChunkUploader 会复用已算 hash
与相册同步并发运行（两个前台服务） 通知栏混淆、网络争用 独立通知渠道 backup_channel；BACKUP_SYNCING 独立原子锁；两者可并行不互斥
设备名变更后历史目录残留 同一手机内容分散在多个设备目录 P0 明确不迁移历史；设备名编辑页提示"仅影响此后新备份的路径"
用户在浏览期间修改/删除源文件 上传时源文件不存在 BackupEngine 捕获 FileNotFoundException → 计失败，原因"源文件已不存在"；不影响其他文件
360 安全套件拦截写入/读取 上传中断 沿用现有项目对策（引导加入信任区）；非本次新增风险
MANAGE_EXTERNAL_STORAGE 被部分应用商店拒绝上架 权限不可用 P0 仅从官网/自有渠道分发；Play Store 上架策略不在本期范围
需确认项：BackupForegroundService 与 SyncForegroundService 并行运行时，服务端是否会因同一用户并发上传产生锁竞争？现有 ChunkUploader 已有 UploadTask 级断点续传与秒传去重，理论上两个并发上传不同文件不冲突；但同一文件被两条链路同时上传时，依赖服务端 upload/init 的幂等性处理——此为既有行为，本期不改变。
